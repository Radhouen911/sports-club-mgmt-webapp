# Sports Club Registration Manager

Design document for Projet 2, "Gestion des inscriptions à un club sportif".
iTeam University, 2026-2027, Dr. Afef Ghabri.
Team: Radhouen boufateh and khalil jaouani.

This is the first milestone. We are not writing the application yet. The goal here is to agree on
what we are building, how the code will be split, and in what order we will deliver it, so the
professor can follow the progression from one commit to the next.

## The records

A member has an id, a last name, a first name, an age and a phone number. The id is generated by
the program, not typed by the user. The phone number stays a string because it can start with a
zero and we never do arithmetic on it.

An activity has a short code (GYM, NAT, TEN), a name, a monthly price and a maximum capacity.

A registration is the link between one member and one activity, plus the date it was made. We
keep it as its own record instead of storing a list of activities inside each member. That makes
cancelling, capacity checks and the "most popular activity" statistic much easier, and it is
also how the assignment presents the data.

## How the code will be organised

We want one responsibility per file. This keeps each file small enough to read in one sitting and
makes it obvious where a change belongs.

    sports_club_mgmt_webapp/
      app.py              creates the Flask app and registers the routes
      models.py           Member, Activity and Registration
      members.py          member logic and validation
      activities.py       activity logic and validation
      registrations.py    enrol, cancel, list by activity
      statistics.py       totals and most popular activity
      db.py               database connection and queries
      schema.sql          table definitions
      templates/          Jinja pages for each screen
      static/             a small stylesheet
      club.db             the SQLite database

The Flask routes live with their section, or in a routes package if the file gets too big. A
route only reads the form, calls the right function and renders a page. Validation and business
logic stay in the modules.

The screens we plan to have:

- a home page with the counts and the most popular activity
- a members page with the list, a search field and links to add, edit and delete
- an activities page with prices and capacities
- a registrations page where you pick a member and an activity, plus a list of who is enrolled
  in each activity

## Storage

The app uses SQLite from the start. It is part of Python, needs no server and lives in a single
file, so the project stays easy to run while still being a real database. The assignment lists
SQLite as an extension, but we prefer to build on it directly instead of writing a text file
layer we would later throw away.

The schema has three tables. Members and activities have a primary key, and registrations use a
primary key on the pair of member and activity, which also stops the same person from being
enrolled twice in the same activity. Foreign keys point back to the two tables, and deleting a
member or an activity removes its registrations.

The connection is opened per request and closed at the end, which is the usual Flask pattern for
SQLite. Queries are kept in the modules that own the data, not scattered through the routes. The
database file, `club.db`, is created from `schema.sql` on first run and is ignored by git.

## Roadmap

1. Design document (this file).
2. Database schema, connection handling and the models.
3. Member module and its pages.
4. Activity module and its pages.
5. Registration module with the duplicate and capacity checks.
6. Statistics and the home page.
7. Cleaning, user guide, and the missing report sections.
8. Final polish.

Each step ends with a working app, not a half finished feature, so the progression is visible in
the git history.
